# Unified LLM implementation audit — 2026-09-23

Scope: current `specs/unified-llm-spec.md`, the active
`src/attractor/llm.lg`, structured-output contract tests, the live provider
runner/checks, and checked-in provider evidence. This is an independent,
targeted audit for the full specification implementation goal. No live API
calls or full-suite run were performed. Findings refer to the pre-repair
worktree; subsequent repair evidence is recorded separately below.

## Concrete implementation gaps

### 1. Unevaluated locations are silently accepted

The validator recognizes these keywords only as schema locations for anchor
discovery; it does not enforce them. Offline public-API probes with
`lg -source-paths src -e` returned:

```clojure
(llm/validate-json-schema {"extra" 1}
  {:type "object" :unevaluatedProperties false})
;; [true ""] — must reject
(llm/validate-json-schema [1]
  {:type "array" :unevaluatedItems false})
;; [true ""] — must reject
```

This affects §4.5, §4.6 and §8.4: both final structured-output APIs call
`parse-validated-object`, which relies on this validator. Tool argument
validation also calls the same public function (§5.8). The proposed annotation
repair addresses a real observable gap, not just an internal cleanup.

The current helpers explain why simply checking leftover keys is insufficient:

- `validate-schema-list` returns only validity/reason, discarding branch results.
- `validate-object-schema` similarly discards successful dependency results.
- `validate-array-schema` replaces absent tail schemas with `true`, losing
  presence information needed to distinguish evaluated from merely allowed.
- `validate-json-schema*` retains the selected conditional branch but discards
  the successful condition result.

Recommended internal representation: return validity/reason plus evaluated
property names and array indices for the current instance, with the public
`[valid? reason]` shape preserved. Child-value validation must remain separate
from in-place evaluation of the current value. Keep reference resource scope
and the existing cycle exception behavior intact.

Semantic acceptance criteria: union every successful `anyOf` branch, all
successful `allOf` branches, the sole successful `oneOf` branch, reference
targets, active dependencies, and successful conditional evaluations. Failed
branches and `not` contribute nothing. A successful `if` contributes even
without `then`/`else`. Missing keywords produce no annotations; explicit `true`
schemas can. `contains` accounts for every matching index. Property-name
checks do not evaluate property values. Child annotations do not leak to the
parent instance. Inner unevaluated constraints cannot see sibling applicator
annotations; outer constraints can consume successful inner results. Apply
unevaluated checks after their contributing keywords, and propagate successful
unevaluated results upward. These rules follow
[JSON Schema 2020-12 core §§7.3, 7.7.1.2, 10 and 11](https://json-schema.org/draft/2020-12/json-schema-core).

Regression cases should include nested objects/arrays, multiple matching
patterns, absent versus explicit additional/items schemas, failing alternatives,
local references/anchors, condition-only schemas, dependency triggers containing
false/null, successful inner unevaluated schemas, and rejection through both
`generate-object` and `stream-object` with unchanged error categories.

### 2. Completed false/null streaming values are reported as unfinished

An offline adapter returning JSON `false` or `null` reproduces an independent
§4.6 bug. `generate-object` returns the valid value, but `stream-object`'s
`:object` accessor throws `:no-object-generated` with “stream did not finish”.
The same adapter returning `0` succeeds in both paths.

The accessor uses `(or @(:object state) ...)`, conflating successful falsy JSON
with the initial state. A separate terminal-success flag or private sentinel
fixes this without changing the public API. It must continue rejecting missing
finish events, schema-invalid final values, cancellation, and provider errors.

### 3. Other schema semantics remain incomplete after unevaluated repair

Offline probes also returned `[true ""]` for:

```clojure
(llm/validate-json-schema "wrong"
  {:$defs {"integer" {:type "integer"}}
   :$dynamicRef "#/$defs/integer"})
(llm/validate-json-schema 1
  {:$schema "http://json-schema.org/draft-04/schema#"
   :minimum 1 :exclusiveMinimum true})
```

The active validator never dispatches on `$schema` or evaluates `$dynamicRef`.
Its reference resolver supports fragment-local references; external/relative
resource references remain unresolved. Meta-schema validation is absent.
Unevaluated implementation therefore cannot justify changing the structured
output story to complete schema conformance. The Attractor spec does not pick
a JSON Schema draft; declare and implement a coherent dialect contract before
claiming full support. Invalid schemas and unsupported declared dialects must
not silently receive a successful validation result.

## Provider conformance evidence

The existing runner is materially broader than older audit summaries. It now
implements 14 of the 15 named §8.9 journeys: text, stream, base64 image, URL
image, single tool continuation, parallel tools, three-round tools, streamed
tools, structured output, reasoning tokens, invalid key, usage accounting,
prompt caching, and provider options. It also includes an agent-loop journey.
The rate-limit/429 journey is still absent from `test/live/provider_matrix.lg`.
`llm_transport_test.lg` has loopback 429/retry checks; that proves local error
handling, not a completed live parity cell.

The checked-in evidence records real progress:

| Capability | Current evidence and limits |
|---|---|
| Parallel / three-round / streaming tools | All six protocol-gateway cells pass in `evidence/provider-tool-protocol-evidence.edn`; parallel checks require executor overlap and both returned values. |
| Provider options / usage | Gateway Responses and Messages cells pass in their `provider-options-protocol` and `provider-usage-protocol` evidence files, with observed wire fields/raw counters. |
| Prompt cache | Messages passes five-turn checks in `provider-cache-protocol-evidence.edn`; Responses `gpt-4.1` passes in `provider-cache-responses-gpt41-evidence.edn`. Earlier mini-model failures remain recorded. |
| Base64 image | Later `provider-capable-image-followup.edn` passes both gateway protocols with exact wire payload and ordered color checks. Earlier mini-model failures are not current proof of an adapter defect. |
| URL image | Both gateway protocols pass in `provider-url-image-evidence.edn`, with exact wire URL checks. |
| Reasoning | Responses GPT-5.2 passes with positive reported tokens. The Messages follow-up is marked failed, despite positive tokens and an Opus response ending in the correct 353; its exact-text predicate also rejects surrounding explanation. Preserve this distinction between normalization and answer formatting. |
| Native first-party endpoints | `test/live/openrouter_protocols.edn` explicitly points `or-responses` and `or-messages` at OpenRouter. These are native protocol adapters, but not the first-party endpoint evidence required by §8.10. The recorded direct Anthropic preflight fails with insufficient balance. No native Gemini live success evidence was found. |

Do not reuse the old `provider-matrix-evidence.edn` “reasoning pass” as current
proof: its Responses detail literally contains `:reasoning false`. The current
`reasoning-evidence` predicate correctly requires positive reported usage.
Similarly, old image checks based on nonempty text are weaker than the newer
wire-plus-content checks.

The §8.10 nonexistent-model → `NotFoundError` smoke step is absent from the
live runner. Its `:text` journey checks a substring and records usage/finish,
but does not assert positive input/output counts and stop completion there.
The separate usage journey covers positive counts. Add an explicit inventory
mapping §8.9/§8.10 requirements to current evidence instead of relying on an
all-pass row count: gateway aliases, model capabilities, test predicate
revisions, and selected subsets can otherwise conceal unproved cells.

## Assessment

Proceed with the annotation repair and the falsy streaming completion fix.
Keep the overall implementation goal active afterward: dynamic references,
dialect handling, native-provider live parity, the missing rate-limit journey,
and the complete integration smoke still lack sufficient evidence. This audit
does not establish the absence of further defects elsewhere in the LLM layer.

## Falsy streaming completion repair

Implemented after the independent audit at the coordinating agent's request.
The structured-stream state now stores a successful final value in a private
`{:value value}` envelope, separating presence from the JSON value. Public
result keys and successful return values are unchanged. Error checking still
precedes the completion lookup.

The regression namespace first ran with 6 tests / 26 assertions and exactly
8 failures, all expected false/null completion failures. It checks both a
finish with an explicit response and a finish using collected deltas, plus
repeat access. Negative cases cover missing finish, tool-call-only finish,
invalid final schema, and a provider error; existing cancellation coverage
remains active.

After repair, this command exited 0 with 12 tests / 65 assertions and zero
failures or errors:

```sh
lg -source-paths src:test test/runner.lg \
  attractor.stream-object-contract-test \
  attractor.schema-recursion-contract-test \
  attractor.stream-accumulator-contract-test
```

`git diff --check` passed. No full suite or live provider call was run for this
bounded fix. The remaining gaps above still apply.
